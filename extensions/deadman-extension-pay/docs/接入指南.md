# 支付能力接入指南

本文面向业务模块与运维：说明如何在宿主应用中接入 **直连支付 / 收付通交易 / 运营打款 / 二级商户进件**。  
模块坐标：`extensions/deadman-extension-pay`；渠道实现见 `plugins/deadman-plugin-pay-wechat`、`plugins/deadman-plugin-pay-mock`。

配套总览见 [README.md](../README.md)；双链路资金隔离见 [双链路资金隔离架构.md](./双链路资金隔离架构.md)。

---

## 1. 能力边界（请按门面接入）

| 能力 | 业务入口 | 推荐门面 | 资金账户 | 说明 |
|------|----------|----------|----------|------|
| 平台自营支付/退款 | 业务 Service | `DirectPayFacade` | BASIC（经营性） | 禁止合单；`fund_lane=DIRECT` |
| 入驻商户合单/分账/退款 | 业务 Service | `EcommerceTradeFacade` | BASIC（分账入账） | 必须合单；`fund_lane=ECOMMERCE` |
| 二级商户进件/绑号 | 业务 Service | `SubMerchantFacade` | — | 渠道无关 SPI |
| 商家转账到零钱 | 业务 Service / Admin | `PayoutFacade` | **仅 OPERATION** | 禁止从 BASIC 打款 |
| 双账户流水 | 财务/业务 | `PlatformFundLedgerService` | BASIC / OPERATION 分表 | 场景与账户硬绑定 |

过渡期仍保留 `PayService` / `RefundService` / `TransferService` / `ProfitSharingService`，但**新代码禁止混用链路**。

**硬约束**

- 渠道插件只实现 SPI，**禁止**自建支付单表。
- 平台单号由本模块生成；业务侧用 `bizOrderNo` 关联。
- 状态变更通过领域事件通知业务。
- 交易佣金代发唯一合规路径：`BASIC 提现 → 对公银行卡 → OPERATION 充值 → PayoutFacade`。

## 2. 依赖与 DDL

### 2.1 Maven

在 `deadman-app`（或组装模块）引入：

```xml
<dependency>
    <groupId>com.mtfm</groupId>
    <artifactId>deadman-extension-pay</artifactId>
</dependency>
<!-- 生产渠道：微信 -->
<dependency>
    <groupId>com.mtfm</groupId>
    <artifactId>deadman-plugin-pay-wechat</artifactId>
</dependency>
<!-- 可选：本地联调 -->
<dependency>
    <groupId>com.mtfm</groupId>
    <artifactId>deadman-plugin-pay-mock</artifactId>
</dependency>
<!-- 转账姓名加密依赖 -->
<dependency>
    <groupId>com.mtfm</groupId>
    <artifactId>deadman-extension-crypto</artifactId>
</dependency>
```

## 3. 配置清单

### 3.1 支付核心 `deadman.plugin.pay`

```yaml
deadman:
  plugin:
    pay:
      enabled: true
      default-provider: wechat-jsapi   # 生产勿用 mock
      test-mode:
        payment:
          enabled: false                # 生产必须 false；开启后覆盖预下单金额
          fixed-amount-cents: 1
        sub-merchant:
          enabled: false                # 生产必须 false；开启后进件不走微信、直接通过
      sync:                           # 待支付主动查单
        scheduler-enabled: true
        cron: "0 * * * * ?"
        min-age: 2m
        max-age: 30m
        batch-size: 50
        parallel-enabled: true
      abnormal-refund:
        # 默认关闭：自动退至商户账户不会按「退给买家」推进业务履约
        auto-enabled: false
        default-receive-type: MERCHANT_BANK_CARD
      refund-sync:
        scheduler-enabled: true
        cron: "30 * * * * ?"
        min-age: 1m
        max-age: 24h
        batch-size: 50
      transfer-limits:
        max-amount-cents: 10000000    # 单次创建总金额上限（分）
        max-bills-per-batch: 500
      transfer-dispatch:
        scheduler-enabled: true
        cron: "15 * * * * ?"
        batch-size: 20
      transfer-sync:
        scheduler-enabled: true
        cron: "45 * * * * ?"
        min-age: 1m
        max-age: 48h
        batch-size: 50
```

### 3.2 微信渠道 `deadman.plugin.pay-wechat`

```yaml
deadman:
  plugin:
    pay-wechat:
      enabled: true
      mock-enabled: false             # 生产必须 false；仅显式 true 才走 Mock 网关
      mch-id: ${WECHAT_PAY_MCH_ID}
      api-v3-key: ${WECHAT_PAY_API_V3_KEY}
      merchant-serial-no: ${WECHAT_PAY_SERIAL_NO}
      private-key-path: ${WECHAT_PAY_PRIVATE_KEY_PATH}
      providers:
        wechat-jsapi:
          enabled: true
          app-id: ${WECHAT_PAY_JSAPI_APP_ID}
          notify-url: https://your-domain/client/api/pay/wechat/jsapi/notify
          refund-notify-url: https://your-domain/client/api/pay/wechat/jsapi/refund/notify
          transfer-notify-url: https://your-domain/client/api/pay/wechat/jsapi/transfer/notify
```

凭证缺失且 `mock-enabled=false` 时启动会失败（不再静默降级 Mock）。

### 3.3 Mock（仅本地）

```yaml
deadman:
  plugin:
    pay:
      default-provider: mock
    pay-mock:
      enabled: true
```

生产 profile（`prod` / `production`）下，`PayProductionSafetyValidator` 会拒绝：`test-mode.payment` / `test-mode.sub-merchant`、`default-provider=mock`、`pay-mock.enabled`、`pay-wechat.mock-enabled`。

### 3.4 转账姓名加密 `deadman.plugin.crypto`

```yaml
deadman:
  plugin:
    crypto:
      enabled: true
      strict-module-key: true
      default-key: ${DEADMAN_CRYPTO_DEFAULT_KEY}   # openssl rand -base64 32
      module-keys:
        pay:
          key-id: pay
          key: ${DEADMAN_CRYPTO_PAY_KEY}
```

未配置密钥时姓名可能明文落库，生产务必配置。

## 4. 支付接入

### 4.1 直连预下单（自营）

```java
PaymentPrepayResult result = directPayFacade.createPrepay(
        PaymentPrepayContext.builder()
                .bizOrderNo(orderNo)
                .description("商品描述")
                .amountTotal(9900)                 // 分
                .payerUserId(userId)
                .channelParams(Map.of("openid", openid))
                .build(),
        "wechat-jsapi");

String outTradeNo = result.outTradeNo();
PaymentClientInvokeParams invoke = result.clientInvokeParams(); // 小程序调起
```

### 4.1b 收付通合单预下单（入驻商户）

```java
PaymentPrepayResult result = ecommerceTradeFacade.createCombinePrepay(
        PaymentPrepayContext.builder()
                .bizOrderNo(combineOutTradeNo)
                .description("合单描述")
                .amountTotal(sumCents)
                .payerUserId(userId)
                .channelParams(Map.of("openid", openid))
                .subOrders(List.of(
                        new PaymentCombineSubOrder(subMchid, subOutTradeNo, "子单", amountCents, true)))
                .build(),
        "wechat-ecommerce-combine-jsapi");
```

流程：短事务落 `NOT_PAY`（带 `fund_lane`）→ 渠道预下单 → 回写 prepayId。客户端用 `invoke` 调起支付。

### 4.1c 收付通退款

```java
ecommerceTradeFacade.createRefund(RefundContext.builder()
        .outTradeNo(outTradeNo)
        .amountRefund(amountCents)
        .amountTotal(totalCents)
        .channelParams(Map.of(PaymentChannelParams.SUB_MCHID, subMchid))
        .build());
```

合单支付单的 `providerId` 为 `wechat-ecommerce-combine-jsapi`，需注册同 ID 的 `EcommerceRefundProvider`（微信已实现）。**必须传 `subMchid`。**

### 4.2 监听支付成功

```java
@EventListener
public void onPaymentStatusChanged(PaymentOrderStatusChangedEvent event) {
    if (!"SUCCESS".equals(event.currentStatus())) {
        return;
    }
    String bizOrderNo = event.order().getBizOrderNo();
    // 幂等更新业务订单：发货/开通会员等
}
```

回调丢失时依赖 `PaymentOrderSyncService` / 内置 `sync` 调度补偿。

### 4.3 业务侧注意

- 金额以支付单 `amount_total` 为准（`test-mode.payment` 会压支付额）。
- 回调带渠道金额时与本地不一致会拒绝落成功（`PAY_AMOUNT_MISMATCH`）。
- 勿在业务大事务内包住 `createPrepay` 的渠道外呼窗口之外的无关写操作放大失败面。

## 5. 退款接入

### 5.1 发起退款

```java
RefundOrderSnapshot snapshot = refundService.createRefund(RefundContext.builder()
        .outTradeNo(paymentOrder.getOutTradeNo())
        .channelTransactionId(paymentOrder.getChannelTransactionId())
        .bizOrderNo(orderNo)
        .amountRefund(amountCents)                 // 分，可部分退
        .amountTotal(paymentOrder.getAmountTotal())
        .reason("协商退款")
        .build());
// snapshot.status(): PROCESSING / SUCCESS / CLOSED / ABNORMAL
```

并发控制：支付单行锁 + 在途（`PROCESSING`/`ABNORMAL`）占用计入可退余额。

渠道明确拒绝（微信业务错误码白名单）→ 本地关单释放占用，**不发业务事件**。  
超时/系统错误等 → 保留 `PROCESSING` 并查单补偿，勿换新单盲重试造成双退。

### 5.2 监听退款终态

```java
@EventListener
public void onRefundChanged(PaymentRefundStatusChangedEvent event) {
    PaymentRefundOrder refund = event.refundOrder();
    String status = event.currentStatus();
    if ("SUCCESS".equals(status)) {
        // 若 userReceivedAccount 以 MERCHANT_BANK_CARD 开头：资金退回商户，勿当买家退款履约
        if (AbnormalRefundReceiveType.isMerchantRecovery(refund.getUserReceivedAccount())) {
            // 运营认领 / 二次打款；不要恢复库存当买家已退
            return;
        }
        // 原子累加业务已退金额、全额则完结
        return;
    }
    if ("CLOSED".equals(status)) {
        // 按「本笔失败」处理；已有部分成功退款时勿整单标失败
    }
}
```

备件订单参考实现：`SparePartOrderRefundListener` + `ClientSparePartOrderService.onRefundSucceeded`。

### 5.3 异常退款（ABNORMAL）

| 配置 | 建议 |
|------|------|
| `abnormal-refund.auto-enabled=false` | 默认；需运营流程再开 |
| `default-receive-type=MERCHANT_BANK_CARD` | 钱退商户户，**不是**退给买家 |

手工发起：`RefundService.createAbnormalRefund(AbnormalRefundContext)`（`USER_BANK_CARD` 须带银行卡与姓名）。

开启自动前请确认：业务监听能识别商户回收，且有买家补偿路径（转账等）。

### 5.4 退款状态机（简）

```
PROCESSING ──► SUCCESS（硬终态）
     │
     ├──► CLOSED（硬终态，明确未受理或渠道关闭）
     └──► ABNORMAL ──(异常退款)──► SUCCESS / …
```

## 6. 商家转账接入

### 6.1 推荐：业务 Service 调门面

```java
TransferBatchVO batch = transferService.createTransfer(new CreateTransferRequest(
        bizOrderNo,          // 幂等键：同号同参返回原批次；改金额/openid/场景会报冲突
        openid,
        amountCents,
        transferSceneId,     // 微信转账场景 ID
        transferRemark,
        userName,            // ≥2000 元建议传；加密落库
        "wechat-jsapi"));    // provider，可空
```

- 只落 `PENDING`，由 `transfer-dispatch` 调度或管理端 `dispatch/run` 外呼。
- 超单笔限额自动拆单；受额度闸门（用户日/日/月）约束。
- 不确定失败保留 `PROCESSING` 并查单；明确拒绝才 `FAIL`。

### 6.2 管理端 API（须授权）

Base：`/api/pay/transfer`

| 方法 | 路径 | 权限 |
|------|------|------|
| GET | `/quota` | `pay:transfer:quota:read` |
| PUT | `/quota` | `pay:transfer:quota:write` |
| POST | `/dispatch/pause\|resume\|run` | `pay:transfer:dispatch` |
| POST | `/` | `pay:transfer:create` |
| GET | `/batches` | `pay:transfer:read` |
| GET | `/batches/{batchNo}` | `pay:transfer:read` |
| POST | `/batches/{batchNo}/stop\|resume` | `pay:transfer:dispatch` |
| POST | `/bills/{outBillNo}/sync` | `pay:transfer:read` |

`pay:transfer:create` 可对任意 openid 出款，生产仅赋高权限角色并审计。额度通过 API 配置，不写死在 yaml。

### 6.3 用户确认收款

渠道返回 `WAIT_USER_CONFIRM` 时明细含 `packageInfo`，需客户端引导用户确认。超时依赖回调/查单，业务应监控长时间非终态。

## 7. 事件与事务约定

| 事件 | 典型监听 | 说明 |
|------|----------|------|
| `PaymentOrderStatusChangedEvent` | 业务履约 | 同步监听加入支付落库短事务 |
| `PaymentRefundStatusChangedEvent` | 业务退款履约 | 同上；异常退款自动处理用 `AFTER_COMMIT`+Async |

建议：

- 业务副作用（库存、会员）与订单更新同本地事务，并对 `outTradeNo`/`outRefundNo` 做幂等。
- 勿在同步监听里再调渠道 HTTP。

## 8. 生产上线检查清单

- [ ] `spring.profiles.active` 含 `prod` 或 `production`（触发 Mock/test-mode 启动校验）
- [ ] `pay.test-mode.payment.enabled=false` 且 `pay.test-mode.sub-merchant.enabled=false`，`default-provider≠mock`

- [ ] 回调 URL 公网可达，与 `notify-url` / Security 放行路径一致
- [ ] `crypto` 已配置 `module-keys.pay`（或 default-key）
- [ ] 退款：`abnormal-refund.auto-enabled` 仅在运营流程就绪后开启

- [ ] 已执行退款/转账相关 migration

## 9. 运维与残留风险（已知可控项）

下列项不阻塞资金底线，但需流程或后续迭代：

| 项 | 说明 | 运维建议 |
|----|------|----------|
| ABNORMAL / 假 PROCESSING | 占用可退余额 | 扫超龄非终态；无 `channelRefundId` 且渠道无单时人工关单 |
| 商户回收语义 | 依赖 `MERCHANT_BANK_CARD` 前缀 | 开 auto 前补 receiveType 或监听分支 |
| 转账查无单卡住 | 占额度不双付 | 人工 FAIL/对账；监控额度占用 |
| 多实例调度 | 无 ShedLock | 派发靠行锁+CAS；查单可能重复外呼 |
| Admin 出款面 | 权限即出款 | 双人复核 / 内网 / 审计 |

渠道错误分类：仅白名单业务拒绝码视为「明确未受理」；其余保留处理中并查单，**禁止**对不确定结果换新单号盲目重试。
