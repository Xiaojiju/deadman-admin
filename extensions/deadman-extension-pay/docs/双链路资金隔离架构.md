# 双链路资金物理隔离架构（pay 模块）

> 依据《微信支付双链路资金物理隔离规范》落地，并预留支付宝等非原生双账户平台的业务隔离扩展。

## 1. 总原则

| 原则 | 说明 |
|------|------|
| 一个服务商主体 | 无需第二套商户号；靠渠道「基本账户 / 运营账户」物理隔离（微信原生；支付宝用业务规则模拟） |
| 三域分离 | **直连支付（DIRECT）**、**收付通交易（ECOMMERCE）**、**运营打款（PAYOUT）** 三套门面，禁止混用 |
| 双账户记账 | `BASIC` 基本账户、`OPERATION` 运营账户；独立流水表、禁止互通记账 |
| 合规中转 | 交易佣金代发唯一路径：`BASIC → 对公提现 → 充值 OPERATION → 商家转账` |

## 2. 三域职责

```text
┌─────────────────┐  ┌──────────────────────┐  ┌─────────────────┐
│ DirectPayFacade │  │ EcommerceTradeFacade │  │  PayoutFacade   │
│ 普通直连支付/退款 │  │ 合单支付/分账/电商退款 │  │ 商家转账到零钱   │
└────────┬────────┘  └──────────┬───────────┘  └────────┬────────┘
         │                      │                        │
         ▼                      ▼                        ▼
   直连商户资金池          收付通 → BASIC           仅 OPERATION
   （记账：BASIC*）        二级商户一清               营销/佣金代发
```

\* 平台自营直连收款记账归入 BASIC（经营性），**禁止**从 BASIC 直接调商家转账。

| 域 | 门面 | 允许的资金账户 | 典型业务 |
|----|------|----------------|----------|
| DIRECT | `DirectPayFacade` | BASIC（自营） | 会员、平台自营商品 |
| ECOMMERCE | `EcommerceTradeFacade` + `SubMerchantFacade` | BASIC（分账入账） | 入驻商户合单、分账、二级商户进件 |
| PAYOUT | `PayoutFacade` | **仅 OPERATION** | 员工佣金代发、拉新奖励 |

## 3. SPI 分层（渠道无关）

```text
spi/
  payment/      PaymentProvider（门面按 DIRECT/ECOMMERCE 约束）
  refund/       RefundProvider / EcommerceRefundProvider（同 providerId 路由）
  ecommerce/    ProfitSharingProvider、SubMerchantProvider
  payout/       TransferProvider（现有）
  fund/         （无渠道 SPI；本地 PlatformFundLedgerService）
```

- **微信**：原生双账户；合单/分账走 ecommerce；转账强制运营账户。
- **支付宝（后期）**：无原生双账户时，仍走同一门面；`PlatformFundLedgerService` 用业务规则强制 BASIC/OPERATION 隔离，渠道实现不得跨域调用。

## 4. 本地账本

| 表 | 账户 | 用途 |
|----|------|------|
| `plugin_pay_basic_account_flow` | BASIC | 分账入账、交易退款、对公提现 |
| `plugin_pay_operate_account_flow` | OPERATION | 对公充值、商家转账支出 |
| `plugin_pay_order.fund_lane` | — | `DIRECT` / `ECOMMERCE`，禁止混用统计 |

场景枚举 `PlatformFundBizScene` 与账户硬绑定；写错账户直接抛错。

## 5. 二级商户抽象

`SubMerchantFacade` + `SubMerchantProvider`：

- `submitApplyment` / `queryApplyment` / `bindExternalSubMchid`（手工绑号 MVP）
- 平台无关字段：`outRequestNo`、`subMchid`、`applymentState`、`shortName`
- 渠道扩展进 `channelPayload`；业务表（如 `merchant_wechat_sub`）只存业务绑定，渠道细节可逐步收敛到 pay 模块快照表。

## 6. 迁移策略

1. **已完成**：双账户流水表 + 三分域门面 + SubMerchant SPI + `fund_lane` + 微信进件/电商退款 Provider；engineering 主调用已切门面
2. **已完成（后续）**：
   - 分账 FINISHED → `PlatformFundLedgerService` 记 BASIC IN（与 `platform_partner_fund_flow` 并存）
   - 退款前分账回退 SUCCESS → 记 BASIC OUT（`ECOMMERCE_PROFIT_SHARING_RETURN_OUT`）；已分账仅允许退剩余全部
   - 电商退款创建/查单/回调走收付通 API，退款单持久化 `sub_mchid`
   - Admin 发起转账/查批/同步经 `PayoutFacade`（强制 OPERATION）
   - 转账明细 SUCCESS → 自动记 OPERATION（`pf_payout_bill:{outBillNo}`）
   - 电商退款：`EcommerceRefundProvider` + `WechatEcommerceRefundProvider`（同合单 providerId）
   - 支付宝模块骨架：`plugins/deadman-plugin-pay-alipay`（默认关闭，双账户靠门面+账本）
3. **仍待**：支付宝 SDK 实装；人工 BASIC 提现/OPERATION 充值记账 API 或管理端；`BASIC_TRADE_REFUND_OUT` 仅在确属平台基本户退款时接入
4. **废弃混用**：`PayService.createPrepay(context, providerId)` 已标记 `@Deprecated`

## 7. 禁止事项（代码级）

- ❌ `DirectPayFacade` 传入合单子单
- ❌ `PayoutFacade` / 转账记账写入 BASIC
- ❌ 分账接收方使用个人 openid（仅服务商商户号）
- ❌ 运营账户参与分账/交易结算
- ❌ 省略 BASIC→对公→OPERATION 中转而直接用交易资金打零钱
